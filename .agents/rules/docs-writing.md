# Documentation Writing Rules

本規範適用於專案中所有文件（Markdown 檔案、README、API 文件、架構說明與開發指引）的撰寫與維護。

---

## 1. 語言與語調 (Language & Tone)

* **語言規範**：
  * 文件主體以流暢、現代的**繁體中文（台灣習慣用語）**撰寫。
  * 專有名詞、程式識別碼、函式名、命令列參數保持**英文原文**，不進行生硬或不常見的直譯（例如：使用 `commit`、`branch`、`PR`、`payload`、`endpoint`）。
* **語調風格**：
  * 專業、精煉、以行動為導向（Action-oriented）。
  * 避免冗言贅字與模糊描述（例如避免「應該可能會...」，改為「若符合條件則觸發...」）。

---

## 2. 文件結構與排版 (Structure & Formatting)

* **標題層級**：
  * 嚴格遵守標題遞進層級（`#` -> `##` -> `###`），禁止跳級使用。
  * 每個主要章節建議於開頭提供 1-2 句話的概述或 TL;DR。
* **程式碼區塊 (Code Blocks)**：
  * 必須標註明確的語言類型（例如 ````bash`、````javascript`、````html`、````css`、````json`），禁止無標註的純程式碼區塊。
  * 終端機指令需明確區分「使用者執行的指令」與「預期輸出」，重要參數需附上說明。
* **表格 (Tables)**：
  * 當涉及多個參數、環境變數、狀態碼或配置選項時，優先採用 Markdown 表格整理，提高閱讀效率。
* **提示區塊 (Alerts)**：
  * 適當使用 GitHub 風格提示塊，突出關鍵資訊：
    * `> [!NOTE]`：補充背景與運作細節
    * `> [!TIP]`：最佳實踐或效率小技巧
    * `> [!IMPORTANT]`：不可忽略的前提或步驟
    * `> [!WARNING]`：潛在風險或版本相容性問題

---

## 3. 程式碼範例規範 (Code Examples)

* **可執行性**：範例程式碼必須語法正確且可重現，避免提供無法直接運行的虛擬片段。
* **安全性**：**嚴禁**在文件或範例中暴露真實的 API 金鑰、密碼、Token 或機密憑證，一律使用佔位符（例如 `<YOUR_API_KEY>` 或 `gho_xxxx`）。
* **檔案路徑**：引用專案檔案時，請使用相對路徑或清楚註記檔案位置（例如：`src/app.js:25`）。

---

## 4. 文件同步與維護 (Maintenance & Sync)

* **程式碼與文件同步**：任何功能新增、重構或移除時，必須在同一個變更階段（Commit / PR）同步更新相關文件（如 README、參數表等）。
* **過期資訊清理**：若功能已廢棄或指令已更動，請即刻修正或刪除舊有指引，避免誤導開發者。
* **連結驗證**：建立內部或外部超連結時，需確保連結有效且路徑正確。
